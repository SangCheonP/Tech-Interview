# 04. 경쟁 상태와 동기화, 데드락

## 대표 면접 질문

> **Q. 공유 데이터에서 경쟁 상태가 생기는 이유와 이를 막는 방법, 데드락과의 차이를 설명해 주세요.**

**30초 답변:** 여러 실행 흐름이 공유 데이터를 동기화 없이 읽고 수정하면 실행 순서에 따라 결과가 달라지는 경쟁 상태가 생길 수 있습니다. 임계 영역을 Mutex나 Lock으로 보호하거나 Semaphore로 동시 접근 수를 제한합니다. 반면 데드락은 작업들이 서로 가진 자원을 기다려 아무도 진행하지 못하는 상태입니다. 락 획득 순서를 통일하는 등의 방법으로 예방할 수 있습니다.

**핵심 키워드:** 공유 자원 · 임계 영역 · 상호 배제 · Semaphore · 교착 상태 · 락 순서

앞 문서에서 운영체제가 Thread를 교대로 실행한다고 배웠습니다. 여러 Thread가 **같은 데이터를 다룰 때**는 명령 사이에 다른 Thread가 실행될 수 있으므로 결과를 점검해야 합니다.

## 경쟁 상태와 임계 영역

`count++`는 읽기·계산·쓰기 단계로 이루어집니다. 두 Thread가 모두 같은 옛 값을 읽으면 한 번의 증가가 사라질 수 있습니다. 경쟁 상태는 공유 자원에 접근한다는 사실 자체가 아니라, **실행 순서가 의도한 결과를 바꾸는 경우**의 문제입니다.

| 개념 | 의미 |
| --- | --- |
| 공유 자원 | 여러 Thread가 함께 접근하는 값·파일 등의 자원 |
| 임계 영역 | 동시에 실행되면 안 되는 공유 자원 접근 구간 |
| 상호 배제 | 한 번에 하나의 실행 흐름만 임계 영역에 들어가게 함 |

```java
public class Counter {
    private int count;

    public synchronized void increment() {
        // 같은 Counter 객체의 잠금을 잡고 한 번에 하나씩 갱신한다.
        count++;
    }

    public synchronized int getCount() {
        // 읽기에도 같은 잠금을 사용해 일관된 값을 본다.
        return count;
    }
}
```

여러 Thread가 **같은 `Counter` 인스턴스**의 메서드를 호출해야 이 예제의 잠금을 공유합니다. 서로 다른 인스턴스의 잠금은 별개입니다. Java의 `synchronized`는 이 예제에서 상호 배제를 구현하는 수단입니다.

## Mutex와 Semaphore

| 도구 | 핵심 역할 | 사용 예 |
| --- | --- | --- |
| Mutex / 상호 배제 잠금 | 임계 영역에 한 실행 흐름만 진입 | 공유 상태 변경 |
| Semaphore | 허가증(permit) 수만큼 동시 진입 제한 | 최대 3개의 작업만 진행 |

잠금은 획득한 쪽이 해제하는 **소유권**을 갖는 방식이 일반적입니다. Java의 `ReentrantLock`도 획득한 Thread가 해제합니다. 반면 Java `Semaphore`의 permit에는 소유권 개념이 없어 다른 Thread가 `release()`할 수도 있습니다. 둘의 목적과 규칙을 혼동하면 안 됩니다.

```java
import java.util.concurrent.Semaphore;

public class LimitedWork {
    private final Semaphore permits = new Semaphore(3);

    public void runTask() throws InterruptedException {
        permits.acquire(); // 동시에 최대 3개 작업만 진입한다.
        try {
            // 제한된 외부 자원을 사용하는 작업
            useResource();
        } finally {
            permits.release(); // 작업이 끝나면 허가증을 반환한다.
        }
    }

    private void useResource() {
        // 예제에서는 실제 외부 호출 대신 작업 자리만 표시한다.
    }
}
```

`finally`에서 반환해야 예외가 나더라도 permit이 누락되지 않습니다. 실제로는 **성공적으로 획득한 permit만** 반환하도록 코드를 구성해야 합니다. 위 코드는 `acquire()`가 성공한 다음 `try`에 들어가므로 그 조건을 만족합니다.

## 데드락은 언제 생길까?

Thread A가 락 1을 가진 채 락 2를 기다리고, Thread B가 락 2를 가진 채 락 1을 기다리면 두 Thread 모두 진행하지 못할 수 있습니다.

| 필요한 조건 | 의미 |
| --- | --- |
| 상호 배제 | 자원을 동시에 사용할 수 없음 |
| 점유 대기 | 가진 자원을 놓지 않고 다른 자원을 기다림 |
| 비선점 | 자원을 강제로 빼앗을 수 없음 |
| 순환 대기 | 서로의 자원을 원형으로 기다림 |

이 네 조건이 **함께 성립할 때** 데드락 가능성이 생깁니다. 실제 데드락이라고 단정하려면 자원 할당과 대기 관계를 함께 확인해야 합니다. 실무에서는 여러 락을 잡을 때 **모든 Thread가 같은 순서로 획득**하도록 정하면 순환 대기를 끊는 데 도움이 됩니다. 시간 제한이 있는 락 시도와 실패 시 복구도 고려할 수 있지만, 타임아웃만 추가했다고 데이터 일관성이 자동으로 보장되는 것은 아닙니다.

```java
synchronized (firstLock) {
    // 모든 작업이 firstLock 다음 secondLock 순서로 획득한다.
    synchronized (secondLock) {
        updateSharedState();
    }
}
```

위 코드는 `firstLock`, `secondLock`, `updateSharedState()`가 준비돼 있다고 가정한 **락 순서 예시**입니다. 실제 코드에서는 메서드와 잠금 대상 객체를 정의해야 합니다.

## 꼬리 질문과 답

- Semaphore의 허가증 수가 1이면 Mutex와 완전히 같나요? 아니요. 동시 접근 수는 같아도 소유권 등 규칙이 다릅니다.
- `volatile`만으로 `count++`를 안전하게 만들 수 있나요? 아니요. 가시성과 복합 연산의 원자성은 다른 문제입니다.
- 데드락을 피하려면? 모든 경로에서 같은 락 순서를 유지하고, 필요한 경우 시간 제한과 실패 처리도 설계합니다.

## 핵심 정리

- 경쟁 상태는 **공유 데이터의 결과가 실행 순서에 따라 달라지는 문제**입니다.
- Mutex는 상호 배제, Semaphore는 동시 접근 수 제한에 초점을 둡니다.
- 데드락은 서로의 자원을 기다리며 진행하지 못하는 상태이며, 락 순서 통일이 대표적인 예방 방법입니다.
