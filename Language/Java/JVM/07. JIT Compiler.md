# JIT Compiler

Java 소스는 `javac`로 Bytecode(`.class`)가 되고, JVM의 Execution Engine이 이를 실행합니다. 이때 HotSpot JVM은 Interpreter와 JIT(Just-In-Time) Compiler를 함께 활용합니다.

## 1. JIT Compiler란?

JIT Compiler는 **프로그램 실행 중** Bytecode의 일부를 해당 CPU에서 실행할 수 있는 기계어(Native Code)로 컴파일합니다. 컴파일된 코드는 이후 실행에서 재사용할 수 있습니다.

```text
.java → javac → .class(Bytecode) → JVM
                                ├─ Interpreter: 해석하며 실행
                                └─ JIT: 실행 중 일부를 기계어로 컴파일
```

Interpreter는 실행을 시작하기 쉽지만 반복 실행되는 코드를 계속 해석해야 합니다. JIT 컴파일에는 시간이 들지만, 자주 실행되는 코드에서는 이후 실행 비용을 줄일 수 있습니다.

| 구분 | Interpreter | JIT Compiler |
| --- | --- | --- |
| 역할 | Bytecode를 해석하며 실행 | 실행 중 Bytecode 일부를 기계어로 컴파일 |
| 초기 비용 | 상대적으로 작음 | 컴파일 시간과 메모리 필요 |
| 반복 실행 | 계속 해석 | 컴파일된 코드를 재사용 가능 |

## 2. 자주 실행되는 코드

HotSpot JVM은 실행 중 정보를 수집하며 자주 호출되는 메서드나 반복 실행되는 코드를 컴파일 대상으로 선택할 수 있습니다. 흔히 이런 코드를 **Hot Code**라고 부릅니다.

```java
public class Main {
    public static void main(String[] args) {
        long result = 0;

        for (int i = 0; i < 1_000_000; i++) {
            // 반복 호출되는 메서드는 JIT 컴파일 대상이 될 수 있다.
            result += add(i, 1);
        }

        System.out.println(result);
    }

    private static int add(int a, int b) {
        return a + b;
    }
}
```

이 코드가 반드시 특정 횟수에 JIT 컴파일된다는 뜻은 아닙니다. 실제 선택과 시점은 JVM 설정, 실행 상태와 컴파일 정책에 따라 달라집니다.

## 3. 실행 정보를 이용한 최적화

JIT는 기계어로 바꾸는 것 외에도 실행 중 수집한 정보를 이용해 코드를 최적화합니다. 대표적인 예가 **메서드 인라이닝**입니다.

```java
private static int add(int a, int b) {
    return a + b;
}

int sum = add(x, 1);
```

JIT가 인라이닝을 적용한다면, 호출 지점에 `add`의 동작을 포함해 메서드 호출 비용을 줄일 수 있습니다. 개념적으로 `sum = x + 1`에 가까워지지만, **실제로 어떤 최적화가 적용되는지는 JVM의 판단에 달려 있습니다.**

## 4. Warm-up

프로그램을 시작한 직후에는 충분한 실행 정보가 없고 JIT 컴파일도 진행 중일 수 있습니다. 반복 실행하면서 자주 쓰는 코드가 최적화되는 과정을 **Warm-up**이라고 부릅니다.

```text
실행 시작 → 실행 정보 수집 → JIT 컴파일·최적화 → 최적화된 코드 실행
```

따라서 Java 코드를 한 번만 짧게 실행해 측정한 시간은 장기간 실행할 때의 성능과 다를 수 있습니다. 이 흐름은 `06. Class Loader`에서 배운 **클래스 준비** 이후, Execution Engine이 실제 코드를 실행하고 최적화하는 단계와 연결됩니다.

## 5. C1과 C2

HotSpot JVM은 일반적으로 **C1**과 **C2** 컴파일러를 사용합니다.

| 컴파일러 | 주요 특징 |
| --- | --- |
| C1 | 비교적 빠르게 컴파일하며 실행 정보를 수집·활용 |
| C2 | 더 많은 비용을 들여 강한 최적화 수행 |

Interpreter와 C1, C2를 상황에 맞게 활용하는 방식을 **Tiered Compilation(단계별 컴파일)**이라고 합니다. 모든 메서드가 `Interpreter → C1 → C2`를 반드시 순서대로 거치는 것은 아닙니다.

## 6. `javac`와 JIT의 차이

| 구분 | `javac` | JIT Compiler |
| --- | --- | --- |
| 실행 시점 | Java 프로그램 실행 전 | Java 프로그램 실행 중 |
| 입력 | `.java` 소스 코드 | Bytecode |
| 주요 결과 | `.class`의 Bytecode | CPU에 맞는 기계어 |
| 목적 | JVM이 사용할 코드 생성 | 실행 중 코드의 성능 개선 |

## 면접 질문

### Q. JIT Compiler는 왜 필요한가요?

Java 코드는 `javac`로 Bytecode가 된 뒤 JVM에서 실행됩니다. HotSpot JVM은 Interpreter로 실행을 시작하면서 정보를 모으고, 자주 실행되는 코드를 JIT Compiler로 기계어로 컴파일할 수 있습니다. 이후 컴파일된 코드를 재사용하고 인라이닝 같은 최적화를 적용해 반복 실행 성능을 높입니다. 다만 컴파일 자체에도 시간과 메모리가 필요하므로 모든 코드가 반드시 JIT 컴파일되는 것은 아닙니다.

## 핵심 정리

- `javac`: 실행 전에 **소스 코드 → Bytecode**.
- JIT Compiler: 실행 중 **Bytecode 일부 → 기계어**.
- 반복 실행되는 코드는 JIT 컴파일과 최적화의 이점을 얻을 수 있습니다.
- JIT 컴파일에는 비용이 들며, 컴파일 대상과 시점은 JVM이 결정합니다.
- Warm-up 때문에 시작 직후와 일정 시간 실행한 후의 성능이 다를 수 있습니다.
- HotSpot의 C1·C2 및 Tiered Compilation은 구현 방식이며 JVM 명세가 강제하는 구조는 아닙니다.
