# 03. CPU 스케줄링

## 대표 면접 질문

> **Q. CPU 스케줄링은 무엇이며, 선점형과 비선점형은 어떻게 다른가요?**

**30초 답변:** CPU 스케줄링은 실행 가능한 작업 가운데 다음에 CPU를 사용할 대상을 정하는 과정입니다. 선점형에서는 실행 중인 작업의 CPU 사용을 중단하고 다른 작업으로 바꿀 수 있습니다. 비선점형에서는 실행 중인 작업을 강제로 빼앗지 않으며, 종료하거나 스스로 대기 상태가 될 때 다른 작업을 실행합니다. 정책에 따라 응답 시간, 처리량, 공정성과 문맥 교환 비용이 달라집니다.

**핵심 키워드:** Ready · Running · 선점 · 비선점 · Time Quantum · 기아 · 응답 시간

앞 문서에서 배운 **문맥 교환**은 실행 대상을 바꿀 때의 동작입니다. 스케줄링은 그 가운데 **누구를 다음에 실행할지 결정**하는 문제입니다. CPU는 보통 실행 가능한 Thread를 스케줄링하며, 교재의 고전적 알고리즘은 편의상 Process 단위의 작업으로 설명하기도 합니다.

## 실행 가능한 작업과 상태

| 상태 | 의미 | 예 |
| --- | --- | --- |
| Ready | 실행할 수 있지만 CPU를 기다림 | 다른 작업이 실행 중 |
| Running | CPU에서 명령을 실행 중 | 계산 수행 |
| Waiting | 이벤트나 I/O를 기다림 | 파일 읽기 완료 대기 |

기다리던 I/O가 끝나면 작업은 Ready가 될 수 있습니다. 운영체제는 CPU 코어마다 실행할 작업을 선택합니다. **한 코어에서는 같은 순간에 한 작업 흐름만 실행**되지만, 여러 코어에서는 서로 다른 흐름이 병렬로 실행될 수 있습니다.

## 선점과 비선점

- **선점형:** 시간 할당량이 끝나거나 더 높은 우선순위의 작업이 준비되는 등 정책에 따라 실행 대상을 바꿀 수 있습니다.
- **비선점형:** 실행 중인 작업을 스케줄러가 강제로 중단하지 않습니다. 작업이 종료되거나 I/O 등으로 스스로 CPU를 놓으면 다음 작업이 실행됩니다.
- **주의:** 선점이 있다고 매번 문맥 교환이 일어나는 것은 아닙니다. 반대로 비선점형에서도 작업이 끝나거나 대기하면 다음 작업으로 전환합니다.

## 대표적인 교재용 정책

| 정책 | 선택 기준 | 생각할 점 |
| --- | --- | --- |
| FCFS | 먼저 도착한 작업 | 긴 작업이 앞서면 뒤 작업의 대기 시간이 길어질 수 있음 |
| SJF / SRTF | 예상 실행 시간이 짧은 작업 / 남은 시간이 짧은 작업 | 실제 실행 시간을 미리 정확히 알기 어려움 |
| Priority | 우선순위가 높은 작업 | 낮은 우선순위 작업의 기아 가능성 |
| Round Robin | 정해진 시간만큼 실행한 뒤 다음 작업 | 너무 짧은 시간 할당량은 전환 비용을 키움 |

**SJF는 보통 비선점형**, 남은 시간이 더 짧은 작업이 오면 전환하는 **SRTF는 선점형**으로 구분합니다. 오래 기다린 작업의 우선순위를 높이는 *에이징(Aging)*은 기아를 줄이는 방법입니다.

여러 큐를 쓰는 **Multilevel Queue**는 작업을 큐별로 나누고, **Multilevel Feedback Queue**는 실행 양상에 따라 큐 사이를 이동시킬 수 있습니다. 큐마다 시간 할당량과 선택 규칙은 설계에 따라 달라집니다. 위 정책은 원리를 비교하기 위한 모델이며, 실제 Linux·Windows 스케줄러가 표의 정책 하나만 그대로 사용한다는 뜻은 아닙니다.

## 성능을 어떻게 비교할까?

| 지표 | 의미 |
| --- | --- |
| 처리량(Throughput) | 단위 시간에 완료한 작업 수 |
| 반환 시간(Turnaround Time) | 도착부터 완료까지 걸린 시간 |
| 대기 시간(Waiting Time) | 실행 가능한 상태에서 CPU를 기다린 시간 |
| 응답 시간(Response Time) | 도착부터 첫 응답까지 걸린 시간 |

목표가 무엇인지에 따라 좋은 정책도 달라집니다. 사용자 입력에는 **응답 시간**이 중요하고, 배치 작업에는 **처리량**이 더 중요할 수 있습니다.

## Java 코드로 연결

```java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            // 실행 중인 스레드가 잠시 대기한다.
            try {
                Thread.sleep(100);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        worker.start(); // 실행 가능한 새 흐름을 만든다.
        worker.join();  // main은 worker의 종료를 기다린다.
    }
}
```

`start()`는 새 Thread를 실행 가능하게 만들지만 **즉시 CPU를 받는다고 보장하지는 않습니다**. `sleep()` 중인 Thread는 대기하며, `join()`을 호출한 main도 완료를 기다립니다. Java 코드만으로 운영체제의 실제 선택 순서를 단정할 수는 없습니다.

## 꼬리 질문과 답

- Round Robin의 시간 할당량이 너무 짧으면? 문맥 교환이 잦아져 비용이 커질 수 있습니다.
- 높은 우선순위 작업만 계속 오면? 낮은 우선순위 작업이 오래 기다리는 기아가 생길 수 있습니다.
- Java Thread 우선순위로 정확한 실행 순서를 제어할 수 있나요? 아니요. JVM과 운영체제의 스케줄링에 의존하므로 순서를 보장하는 수단으로 쓰지 않습니다.

## 핵심 정리

- **스케줄링은 다음 실행 대상을 선택**, 문맥 교환은 선택 후 실행 상태를 바꾸는 과정입니다.
- 선점 여부와 선택 정책에 따라 응답성, 처리량, 공정성과 비용이 달라집니다.
- 교재 알고리즘과 실제 운영체제 구현은 구분해서 이해합니다.
